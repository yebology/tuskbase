# Tuskbase — Architecture Overview

## System Overview

Tuskbase is a verifiable AI research agent. It has three layers:

```
Frontend (Next.js) → Backend (Hono) → External Services (Walrus, MemWal, Tatum, Sui, OpenAI, Tavily)
                                    → Database (PostgreSQL)
```

## Monorepo Structure

```
tuskbase/
├── frontend/          # Next.js — single-page research UI
├── backend/           # Hono — API + research orchestration + PDF generation
├── contracts/         # Move — Sui smart contracts
└── docker-compose.yml # Orchestration
```

Each folder is independent — own `package.json`, own `Makefile`, own build.

## Data Flow

### Research Flow (main flow)
```
User query → POST /api/research
  → AI detectIntent (OpenAI)
  → [web_research]:
      Tavily (20 sources)
      → OpenAI extractFacts (3-5 per source)
      → MemWal remember (all facts, parallel)
      → OpenAI generate (summary + analysis + conclusion)
      → PDFKit generate report
      → Walrus store PDF
      → Sui record on-chain (1 tx via Tatum RPC)
      → Walrus store final PDF (with provenance filled)
  → [blockchain_*]: Tatum MCP Data API → OpenAI format
  → Response (chat summary + PDF download URL)
```

### Verify Flow
```
Report selected → POST /api/memory/verify
  → Walrus: blob exists?
  → Walrus: retrieve + hash check
  → Tatum RPC: tx exists on Sui?
  → Response (isValid + details)
```

### Recall Flow
```
Query → POST /api/memory/recall
  → MemWal SDK: semantic search
  → Response (matching memories)
```

## Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| Hono over Express | Lightweight, fast, TypeScript-first |
| DI Container | Testable, swappable services, no global state |
| Use Cases pattern | Business logic separated from routes and services |
| PDFKit for reports | Full control over layout, no browser dependency |
| 20 sources per query | Deep research, not just a quick search |
| 1 Sui tx per report | Scalable — not 100 txs per query |
| Two-pass PDF | First pass for hash, second pass with provenance filled |
| Public Sui RPC for tx | Tatum gateway doesn't support all SDK methods |
| Tatum for verification | Read-only operations work fine via Tatum |
| MemWal for memory | Semantic recall across sessions, encrypted |
| localStorage for chat | Frontend persistence without backend dependency |
| No auth (yet) | Single-user hackathon demo |

## Communication

- Frontend → Backend: REST (JSON over HTTP)
- Backend → Walrus: HTTP PUT/GET (blobs)
- Backend → MemWal: SDK (HTTP under the hood)
- Backend → Sui: @mysten/sui SDK via public RPC (for transactions)
- Backend → Tatum RPC: JSON-RPC (for verification/reads)
- Backend → Tatum MCP: @tatumio/blockchain-mcp API client
- Backend → OpenAI: openai SDK
- Backend → Tavily: HTTP POST
- Backend → PostgreSQL: Prisma ORM

## PDF Report Structure

Generated by `PdfService` using PDFKit:

1. **Cover Page** — title, metadata (date, source count, verification status)
2. **Table of Contents** — auto-generated section list
3. **Executive Summary** — 150-250 word overview (AI-generated)
4. **Key Findings** — facts grouped by source, with trust scores and citations
5. **Detailed Analysis** — 300-500 word analysis connecting facts (AI-generated)
6. **Conclusion & Recommendations** — takeaways + next steps (AI-generated)
7. **Sources** — all sources with URLs and trust scores
8. **Provenance Verification** — report hash, Sui tx, Walrus blob ID, verification instructions

## On-Chain Provenance Model

One Sui transaction per research report (not per-fact):
- `blob_id` → Walrus blob ID of the final PDF
- `content_hash` → SHA-256 of the PDF (base64 encoded)
- `source_url` → `tuskbase://research/{query}`
- `trust_score` → 9 (self-generated report)

Individual facts are stored in MemWal for semantic recall but NOT individually on-chain.
This keeps gas costs low and latency manageable with up to 20 sources.
